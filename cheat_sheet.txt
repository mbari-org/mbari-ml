mbari-ml Cheat Sheet
========================================
Described in: Lundsten, Barnard & Caress (2026), "mbariml: a curation pipeline
for turning deep-sea imagery and video into object-detection training data",
arXiv:2609.25500 -- https://arxiv.org/abs/2609.25500

Regenerated for the unified `mbariml` CLI (v0.21.0). The full, authoritative
--help output for every command is captured verbatim at the bottom of this
file -- if this walkthrough and --help ever disagree, trust --help (it's
generated straight from the code, not hand-maintained).

SETUP
-----
    pip install -e .
This installs the `mbariml` command (see pyproject.toml). Confirm it worked:
    mbariml --help
requirements.txt is also kept, for anyone who just wants
`pip install -r requirements.txt` without an editable install.

Because that's an *editable* install, editing any .py file takes effect the
next time you run `mbariml` -- no reinstall needed. Re-run `pip install -e .`
only when pyproject.toml changes (a new dependency, mainly).

FOUR PHASES (not numbered steps)
---------------------------------
Numbered steps were dropped in v0.11.0. They'd been renumbered three times as
commands merged and moved, each renumbering rippling through every docstring
and both docs, for a sequence that was never actually linear. What the
pipeline really is:

    INGEST   infer images | infer video       pixels + detections -> database
    ENRICH   embed | cluster | refine         embeddings and grouping
    CURATE   review | remap-labels            human review and relabeling
    EMIT     export {voc,yolo,id,html,stats}  annotations, galleries, numbers
             query

Every command reads and writes the SAME database schema (see mbariml.db), so
any command's output is usable by any other that needs what it has. That's
what lets you start anywhere: point `infer video` at new footage and go
straight to `review` on its output, or run `embed`/`cluster` over a database
any ingest command produced.

HOW TO READ A TYPER COMMAND (read this once)
---------------------------------------------
Every command has the shape:
    mbariml <command> [ARGUMENTS] [OPTIONS]

Some commands are grouped: `mbariml infer images`, `mbariml export voc`.
`infer` and `export` aren't runnable themselves -- they just group their
subcommands. Run `mbariml infer --help` to see a group, `mbariml infer video
--help` for one subcommand's own arguments/options.

- ARGUMENTS are positional, required, and passed in order with no flag --
  e.g. in `mbariml infer images models/best.pt /data/images/ /data/out/` the
  three paths are matched to model_path / input_dir / output_dir purely by
  position. They show as `{name}` in the Usage line.
- OPTIONS start with `--` and go anywhere after the arguments. Optional
  unless --help marks them `[required]`; most show a `[default: ...]`.
- Boolean options come as on/off pairs, e.g. `--random` / `--no-random`.
- `--help` works on every command. Always available, always accurate.
- Nothing here silently does nothing: a bad path or value raises immediately,
  and unexpected failures print a full traceback and exit non-zero.


==============================================================================
INGEST -- get pixels and detections into a database
==============================================================================

infer images
  Run a model over a directory of images (searched recursively), crop every
  detection as an ROI, and store it all in a curation database.

    mbariml infer images models/best.pt /data/survey_images/ /data/results/

  This is the merge of what used to be two commands, `detect` and
  `infer-images` (v0.11.0). They wrote the same schema and cropped ROIs the
  same way; the whole real difference was batching, annotated-image saving,
  and a 16x gap in the default confidence. That distinction survives as
  --preset:

    --preset curate    conf 0.005, imgsz 1952, no annotated images  [DEFAULT]
                       Mine everything, then cluster/review and throw away the
                       noise. Default deliberately: an over-permissive
                       threshold is recoverable (filter later -- the review
                       GUI even has a min-confidence slider), a too-strict one
                       silently drops detections you can't get back without a
                       full re-run.
    --preset predict   conf 0.08, imgsz 992, saves annotated images
                       Believable predictions over new imagery.

  Any individual option overrides its preset: `--preset predict --conf 0.2`
  does what it says.

  Other useful options: --limit N (quick test, or right-size a real run),
  --random (with --limit, sample across the whole directory rather than taking
  a contiguous chronological slice), --seed N, --batch-size, --export-csv
  (taxa-by-image count matrix), --device auto|mps|cuda|cpu

  Produces: /data/results/yolo_predictions.duckdb, names.txt

infer video
  Run a model over video. Two modes, for two different jobs.

  --mode track  [DEFAULT]  ONE ROI per tracked object.
    This is what you want for building curation/training data out of video.
    A sponge in view for 300 frames is one animal, not 300 training examples
    -- 300 near-identical crops would swamp clustering and be tedious to
    review. Measured on a real ten-second benthic clip: 711 detections
    collapsed to 7 tracks, so 7 ROIs.

      mbariml infer video models/best.pt /data/dive_video/ /data/results/

    --tracker    Ultralytics tracker config. Default `tracktrack.yaml` (the
                 CVPR 2025 tracker Ultralytics ships). Other shipped names:
                 botsort.yaml, bytetrack.yaml, ocsort.yaml, deepocsort.yaml,
                 fasttrack.yaml -- or a path to your own YAML:

      mbariml infer video models/best.pt clip.mp4 /data/results/ \
          --tracker /path/to/my_tracker_settings.yaml

                 IMPORTANT: how many tracks you get is governed by the
                 TRACKER's thresholds (track_high_thresh, new_track_thresh),
                 not just --conf. Lowering --conf alone will not produce more
                 tracks; copy the tracker YAML and lower its thresholds.

    --track-roi  Which frame of a track becomes its ROI:
                   best-conf-central [DEFAULT] most confident frame of the
                        track's MIDDLE THIRD. The first and last frames of a
                        track are when the animal is entering/leaving view --
                        clipped at the frame edge, occluded, motion-blurred --
                        and plain max-confidence happily picks exactly those.
                   sharpest-central  least blurry frame of the middle third
                        (Laplacian variance), when crop quality matters more
                        than detector confidence.
                   best-conf         most confident frame of the whole track.
                   center            middle frame, ignoring confidence.
                 Tracks too short for a middle third fall back automatically.

    --min-track-length N   ignore tracks with fewer than N observations.

  --mode stride  Sample every Nth frame and treat each as an independent
    image. No tracking, so the same animal is detected repeatedly.

      mbariml infer video models/best.pt clip.mp4 /data/results/ \
          --mode stride --stride 60

  Both modes take the same --preset/--conf/--iou/--imgsz/--device as
  `infer images`, and accept a single video file or a directory of them.

  What lands on disk: each frame that produced a detection is extracted to a
  real JPEG under OUTPUT_DIR/frames/, and image_path points at THAT file.
  Video rows are therefore indistinguishable from image rows to everything
  downstream -- review, embed, cluster, all four exports, html, stats all
  work unchanged, with no video-aware code anywhere else in the pipeline.
  Frames with no detections are never written.

  The trail back to the footage is kept in provenance columns
  (video_path, frame_number, frame_time_s, track_id, track_length), which is
  what the review GUI's "Open Video" button uses. Only frames that produced a
  detection are extracted, so tracking mode writes roughly one JPEG per track.

  Same database or separate? Either. Ingest commands allocate ids from the
  database's own counter, so a second run appends instead of colliding --
  several videos, or images and video, can share one database and be
  clustered/reviewed together. Verified directly: 5 image rows + 4 video rows
  in one database, ids 0..4 and 5..8, stats aggregating across both.


==============================================================================
ENRICH -- embeddings and grouping
==============================================================================

embed
  Compute a DINOv3 embedding for every ROI that doesn't have one yet.

    mbariml embed /data/results/yolo_predictions.duckdb

  Three speed levers, all tuned by default: --batch-size (32) ROIs per GPU
  forward pass, --decode-workers (~16) threads for CPU-side decode, and
  --flush-size (2000) embeddings per bulk DB UPDATE. The last matters most --
  DuckDB is dramatically slower at many small UPDATEs than one bulk UPDATE,
  which is what once made a run decay from ~45 it/s to ~6.5 it/s and keep
  falling. Safe to Ctrl-C and re-run: only rows with embedding IS NULL are
  processed.

  Changed the embedding model, or mixing databases? Recompute everything --
  never mix two models' embeddings in one database:

    mbariml embed /data/results/yolo_predictions.duckdb --force

cluster
  Cluster embeddings with EVoC, tag each cluster with its dominant label, and
  write review grids to roi_grids/.

    mbariml cluster /data/results/yolo_predictions.duckdb

  Tuning knobs if the separation looks wrong -- e.g. clearly distinct things
  landing in "noise":
    --approx-n-clusters N   target cluster count [default: 18]; pass 0 to let
                            EVoC choose
    --noise-level F         0.0-1.0 outlier sensitivity [default: 0.2]; lower
                            calls fewer points noise
    --base-min-cluster-size, --n-neighbors, --min-samples, --seed
    --naming auto|dominant|indexed
                            how clusters are named in new_label [default: auto].
                            Clusters are named after the dominant label of their
                            members -- which breaks for a single-class detector
                            (e.g. Megalodon, which only reports "object"), since
                            then every cluster gets the same name and the
                            grouping is lost. 'auto' appends an index whenever
                            one label wins several clusters, so you get
                            object_1, object_2, ... 'dominant' always uses the
                            bare label; 'indexed' always suffixes.
    --label-source original|new
                            WHICH label the naming vote reads [default:
                            original]. 'original' is the raw detector class;
                            'new' is your curated new_label, falling back to the
                            raw class for rows you haven't reviewed.
                            Use 'new' when re-clustering a database that has
                            already been through review -- with the default, a
                            reviewed single-class database comes back as
                            object_1, object_2, ... and the taxon names you
                            typed are gone. Measured on 300 curated ROIs:

                              --label-source original -> object_1/2/3
                              --label-source new      -> Muusoctopus,
                                                         Sponge_sp_A,
                                                         Coral_bamboo

                            Caveat: 'new' reads the column clustering writes
                            back to, so running it twice feeds the first run's
                            generated names back in. It's for the first pass
                            over a reviewed database, not repeated re-runs.

  !! CLUSTERING OVERWRITES new_label FOR EVERY EMBEDDED ROW, verified rows
     included, whichever --label-source you pick. It doesn't merge, there's no
     undo, and `verified` is NOT cleared -- so afterwards those rows still look
     human-reviewed while carrying a machine-generated label. To experiment
     without risking a curated database, copy it and cluster the copy:

       mkdir -p ~/Desktop/cluster_experiment
       cp /data/results/yolo_predictions.duckdb ~/Desktop/cluster_experiment/
       mbariml cluster ~/Desktop/cluster_experiment/yolo_predictions.duckdb \
           --label-source new --seed 42

     Copy it into its OWN directory -- cluster writes roi_grids/ next to the
     database, so a same-directory copy drops grids on top of the originals.
     The copy carries the embeddings, so `embed` never re-runs and each
     clustering iteration is seconds. Always pass --seed while tuning, or you
     can't tell whether a change to the other knobs did anything.

  RECIPE: test clustering on a curated database, safely
  -----------------------------------------------------
    # 1. Close the review GUI, then check nothing is mid-write. A .wal
    #    sidecar means an open connection hasn't flushed and the copy
    #    would be incomplete.
    ls /data/results/yolo_predictions.duckdb*
    du -h /data/results/yolo_predictions.duckdb

    # 2. Copy into its own directory.
    mkdir -p ~/Desktop/cluster_experiment
    cp /data/results/yolo_predictions.duckdb ~/Desktop/cluster_experiment/

    # 3. Baseline: what do the curated labels look like now?
    mbariml export stats ~/Desktop/cluster_experiment/yolo_predictions.duckdb

    # 4. Cluster the COPY, naming clusters from your curated labels.
    mbariml cluster ~/Desktop/cluster_experiment/yolo_predictions.duckdb \
        --label-source new --approx-n-clusters 24 --seed 42

    # 5. Compare, then look at the groupings.
    mbariml export stats  ~/Desktop/cluster_experiment/yolo_predictions.duckdb
    mbariml review ~/Desktop/cluster_experiment/yolo_predictions.duckdb

  The real database at /data/results/ is never opened by any of this.

  To try different settings, start each attempt from a FRESH copy rather than
  re-running cluster on the same file -- '--label-source new' reads the column
  clustering writes back to, so a second run on the same file votes on the
  first run's generated names as if a human had chosen them:

    rm -rf ~/Desktop/cluster_experiment && mkdir -p ~/Desktop/cluster_experiment
    cp /data/results/yolo_predictions.duckdb ~/Desktop/cluster_experiment/
    mbariml cluster ~/Desktop/cluster_experiment/yolo_predictions.duckdb \
        --label-source new --approx-n-clusters 40 --noise-level 0.1 --seed 42

  No merge path back: if an experiment is better, re-review in the copy and
  adopt it as your working database, or carry specific renames across with
  remap-labels. Nothing splices new clusters into a curated database while
  preserving the human labels.

refine (optional)
  Re-cluster ONE label's ROIs into finer sub-clusters -- for when clustering
  lumped something too coarsely (a big catch-all "noise" bucket, etc.).

    mbariml refine /data/results/yolo_predictions.duckdb /data/results/ --new-label noise


==============================================================================
CURATE -- human review
==============================================================================

review (interactive GUI)
  Label and delete ROIs by hand.

    mbariml review /data/results/yolo_predictions.duckdb
    mbariml review /data/results/yolo_predictions.duckdb --label noise

  In the grid: click to select, Shift-click for a range, Ctrl/Cmd-click to
  add; arrow keys navigate/extend. Type a label into the relabel field (free
  text, or pick from the dropdown of labels already in use) and press Enter,
  or click Label, to apply it to the selection. Right-click an ROI to rank
  EVERY ROI in the database by embedding similarity to it -- the whole
  dataset, not the page you're on; the most similar rows are then pulled
  onto page 1 from wherever they were. Needs `embed` to have run, and the
  status bar says how much of the dataset was actually ranked ("all 8,412
  matching ROIs", or "3,001 of 8,412 -- 5,411 not embedded yet" if `embed`
  was interrupted or run with --limit, which is the one thing that can
  narrow the search).
  Delete removes the selection (asks first -- permanent); Escape clears it. A
  tile-size slider and a "Hide verified" checkbox control what's shown, and
  Brightness/Contrast sliders below the tile-size slider stretch the
  thumbnails across the whole grid -- faint animals against sediment are much
  easier to pick out that way. Both are view-only (stored ROIs are never
  modified); "Reset" puts them back to neutral.

  The right panel shows the full source image with mouse-wheel zoom and
  click-drag pan, overlaying EVERY detection on that image -- not just the
  current page's rows. Drag a box's handles to resize/reposition it (saved
  immediately, crop regenerated); the selected box shows red, the rest pale
  blue-grey; right-click a box for "Delete".

  "+ Add New ROI" (green, top of the controls panel) -- for a detection the
  model missed entirely. Click it, drag a box on the image, type a label, and
  keep going until you click it again or press Escape. Each box is saved the
  moment you label it (confidence 1.0, verified set -- a human drew it), and
  its embedding is computed in the background using the same DINOv3 model
  `embed` uses, so it's immediately usable by similarity search/clustering.

  "Open Video" (next to Delete) -- for ROIs that came from `infer video`.
  Opens the SOURCE FOOTAGE at the exact moment this detection was made, using
  the row's video_path + frame_time_s. Tries IINA, then mpv, then VLC (all of
  which honor a start position), falling back to your browser with a #t=
  media fragment. Greyed out for ROIs that came from still images.

remap-labels
  Bulk-rename new_label values from a two-column CSV (old_label,new_label per
  row, no header).

    mbariml remap-labels /data/results/yolo_predictions.duckdb changes.csv

  Every pair is applied in ONE pass against the original state, so a changes
  file that swaps two labels (A,B then B,A) actually swaps them. Applying
  them sequentially -- as this once did -- turned every A into B and then
  every B (including the just-renamed As) back into A, silently collapsing
  both labels into one.


==============================================================================
EMIT -- annotations, galleries, numbers
==============================================================================

export voc | yolo | id | html | stats
  Export curated labels to whichever downstream format you need, generate an
  HTML gallery for visual QA, or print the summary numbers. `stats` is an
  export subcommand because it reports the same population the annotation
  exports write -- it's a preview of what a training set will hold, not a
  separate kind of output. (It used to be top-level `mbariml stats`; that
  name is gone, so there is no question which is canonical.)
  `export yolo` also writes the Ultralytics
  dataset YAML (<output_dir name>.yaml) -- split paths, nc, names -- whose
  nc/names come from the same list that numbered the classes in labels/, so
  they cannot drift apart. Its split paths are relative and it has no `path:`
  key, so Ultralytics resolves them against the YAML's own directory: name
  the YAML at training time and the folder works from any mount (/Volumes on
  the Mac, /mnt on the trainer). An empty split is omitted, so '85 15 0'
  writes no `test:` key rather than one pointing at an empty file.

    mbariml export yolo predictions.duckdb \
      /Volumes/M3_ML/training_data/2026/MBARI_lassml_my_survey_20260916/ \
      --split-ratios '85 15 0' \
      --yaml-name MBARI_lassml_my_survey_20260916_yolo26s_LL.yaml


  What gets exported, for all of them (and for stats):
    verified, name unchanged  -> exported, named with the original detector label
    verified, name updated    -> exported, named with new_label
    NOT verified              -> not exported at all
  ("noise" is excluded either way.) The Verify button in `review` sets
  verified WITHOUT writing new_label -- only relabelling writes it -- so
  filtering on new_label alone silently drops every box you confirmed but
  did not retype. html and stats take --include-unverified to fall back to
  raw detector output on an unreviewed database; the dataset exports do not.
  All
  four locate images via the path recorded at ingest -- no image_dir argument
  -- and name output files after the source image's own filename, adding a
  <parent_dir>_ prefix ONLY to names that would otherwise collide (and
  logging when they do), so two dives sharing a filename never silently
  overwrite each other.

    mbariml export voc  /data/results/yolo_predictions.duckdb /data/results/voc_out/
    mbariml export yolo /data/results/yolo_predictions.duckdb /data/results/yolo_out/
    mbariml export id   /data/results/yolo_predictions.duckdb
    mbariml export html /data/results/yolo_predictions.duckdb /data/results/html

  voc   Pascal VOC XML, one file per image, in pascal_voc/, plus
        new_names.txt (every distinct label used).
  yolo  A complete trainable dataset skeleton: YOLO label files in labels/
        (normalized `class_id x_center y_center width height`), names.txt in
        class-index order, and train.txt/val.txt/test.txt listing images as
        RELATIVE `./images/<file>` paths -- one per line, so the directory
        can be zipped and moved to a training box without rewriting a thing.
        Add the images with the copy script (see below):

            mbariml export yolo /data/results/yolo_predictions.duckdb /data/results/yolo_out/
            python3 /data/results/yolo_out/copy_images.py --dest /data/results/yolo_out/images

        The filenames match by construction, so `images/X.jpg` pairs with
        `labels/X.txt` the way YOLO expects (it swaps /images/ for /labels/).

        Split options: --split-ratios "85 10 5" (default, must sum to 100),
        --split-seed 42 (default -- same db + ratios + seed always gives the
        same split, so re-exporting after relabelling a few ROIs doesn't
        silently reshuffle what was held out and make two trained models
        incomparable), --test-images-file FILE to pin a fixed benchmark set
        into test every time, and --no-splits to skip them entirely.
        Splitting is per IMAGE, never per box: two crops of one frame on
        opposite sides of the train/val line leak the same background and
        often the same animal across the split.
  id    A *.id sidecar per source image with a curated identification --
        header records the model, who ran it, when, the full source path and
        the image's pixel dimensions, plus a legend for every column. Each
        identification is one CSV row:

          index,label,confidence,center_x,center_y,lon,lat,depth,
          tl_x,tl_y,tr_x,tr_y,br_x,br_y,bl_x,bl_y

        Every value is comma-separated, so csv.reader/pandas read it
        directly; rows are written with csv.writer, so a label containing a
        comma is quoted rather than shifting every column after it.
        lon/lat/depth appear ONCE, beside the center -- they describe where
        the observation is, and an observation has one position.
        center_x/center_y are the exact integer midpoint of the tl/br
        corners, so the file never disagrees with itself. Corner values are
        box EDGES: a box flush against the right of a 1936-wide frame has
        tr_x 1936, one past the last column, which is what makes
        width = tr_x - tl_x exact -- do not clamp it. image_width/height are
        read from the image header only (~6ms/image, 'unknown' if it moved).
        Writes next to the originals by default, so it takes no positional
        output_dir:

            mbariml export id /data/results/yolo_predictions.duckdb
            mbariml export id /data/results/yolo_predictions.duckdb --output-dir ~/Desktop/ids

        --output-dir collects them in one directory instead -- for a
        read-only survey volume, or a handoff without the imagery. Names
        there are the image's own filename, with a <parent_dir>_ prefix
        added only where two images would otherwise collide -- flattening a
        nested mission tree is exactly when two dives' same-named images
        would otherwise overwrite each other.
  html  Paginated gallery of images and their labeled crops (writes its own
        images/ and crops/, so it needs no manifest).

export stats
  Label counts (with percent), boxes-per-image summary stats
  (avg/min/median/max), and optionally an image x label count matrix CSV for
  ecological analysis. Counts the same verified localizations the exports
  write, named new_label where you retyped it and the raw detected label
  where you confirmed it unchanged -- so these numbers preview what a
  training set will hold. --include-unverified counts raw detections too.

    mbariml export stats /data/results/yolo_predictions.duckdb --output-dir /data/results/stats/
    mbariml export stats /data/results/yolo_predictions.duckdb --exclude-noise --top 20
    mbariml export stats /data/results/yolo_predictions.duckdb --include-unverified



  Produces (with --output-dir): stats/label_by_image_matrix.csv -- rows are
  images, columns are labels, values are counts. Read it straight into
  pandas/R/Excel for per-image richness, frequency-of-occurrence, etc.

query
  Any SQL you want against the database -- spot checks, counts, one-offs.

    mbariml query /data/results/yolo_predictions.duckdb \
        "SELECT new_label, COUNT(*) FROM predictions GROUP BY 1 ORDER BY 2 DESC"

Image manifest + copy_images.py (written by `export voc` / `export yolo`)
  Both write annotation files, not image copies -- the source images already
  exist wherever ingest found them. Each also writes image_manifest.csv
  (source_path -> dest_filename, the image's own name unless it collides)
  and a standalone
  copy_images.py. Run that later to pull the actual images down:

    python3 /data/results/voc_out/copy_images.py
    python3 /data/results/voc_out/copy_images.py --dest ~/Desktop/my_training_images

  For a YOLO export specifically, point it at an images/ directory INSIDE the
  export -- that's the directory train/val/test.txt's ./images/ paths mean:

    python3 /data/results/yolo_out/copy_images.py --dest /data/results/yolo_out/images

  copy_images.py is stdlib-only and doesn't import mbariml -- it runs
  standalone, from any machine that can see the recorded source paths.


==============================================================================
SHORTCUT: RUN THE WHOLE CHAIN AT ONCE
==============================================================================
`mbariml run` chains ingest -> embed -> cluster -> export (voc + html):

    mbariml run models/best.pt /data/survey_images/ /data/results/

Video works too -- the chain is identical after ingest:

    mbariml run models/best.pt /data/dive_video/ /data/results/ --media video

Start or stop partway with --from/--to (named stages: ingest, embed, cluster,
export) -- e.g. to resume after reviewing in the GUI and just re-export:

    mbariml run models/best.pt /data/survey_images/ /data/results/ --from export

Reaching the export stage runs both `export voc` and `export html`. Want just
one? Run it directly rather than through `run`.

--random/--seed (ingest image sampling) and --approx-n-clusters/--noise-level
(clustering) pass through, sharing one --seed for a reproducible run:

    mbariml run models/best.pt /data/survey_images/ /data/results/ --limit 1000 --random --seed 42

For every other EVoC knob, run `mbariml cluster` directly.

`review`, `query`, `remap-labels`, `export stats`, `export yolo`, and `export id`
aren't in the chain -- they're interactive, or they don't belong in the
middle of a batch run. Run them directly, any time.

mbariml run --help


 Usage: mbariml run [OPTIONS] {model_path} {input_path} {output_dir}

 Run the scriptable chain (ingest -> embed -> cluster -> export: voc + html).

 Every stage reads/writes OUTPUT_DIR/yolo_predictions.duckdb, so re-running
 with --from past ingest resumes against whatever is already in that
 database -- nothing upstream is re-run or overwritten.

╭─ Arguments ──────────────────────────────────────────────────────────────────────────────────────╮
│ *    model_path      <str>  Path to the YOLO model (used by the ingest stage). [required]        │
│ *    input_path      <str>  Directory of images, or a video file/directory (see --media).        │
│                             [required]                                                           │
│ *    output_dir      <str>  Directory for the database and all stage outputs. [required]         │
╰──────────────────────────────────────────────────────────────────────────────────────────────────╯
╭─ Options ────────────────────────────────────────────────────────────────────────────────────────╮
│ --media                               <str>    What INPUT_PATH holds: 'images' or 'video'.       │
│                                                [default: images]                                 │
│ --from                                <str>    First stage to run: one of ['ingest', 'embed',    │
│                                                'cluster', 'export'].                             │
│                                                [default: ingest]                                 │
│ --to                                  <str>    Last stage to run (inclusive): one of ['ingest',  │
│                                                'embed', 'cluster', 'export'].                    │
│                                                [default: export]                                 │
│ --limit                               <int>    Limit passed through to stages that support it,   │
│                                                for a quick test run.                             │
│ --random               --no-random             With --limit, sample images randomly at ingest    │
│                                                instead of taking the first N in sorted order.    │
│                                                [default: no-random]                              │
│ --seed                                <int>    Random seed, shared by --random image sampling    │
│                                                and EVoC clustering, for a reproducible run.      │
│ --approx-n-clusters                   <int>    Passed through to cluster; see `mbariml cluster   │
